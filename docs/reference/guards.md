## Details

- **`.\tests\test-profiles.ps1`** is the primary harness. Runs **every live profile by default** (`profiles/*.sh` except `select-model.sh` — currently 6; parked ones in `profiles/parked/` are excluded automatically. `-Profile <name>` runs one). Each profile is checked against an **intent manifest**: purpose string, expected `DEV_TIERS_*` flags, expected `OPENCODE_MODEL`/`OPENCODE_SMALL_MODEL` (GoDefault profiles must leave them unset), and whether the main seat is **tool-capable** (`tool_call` in the resolved config — a profile seating a model that cannot call tools is a FAIL; the old role-based check was removed 2026-09-17 as both obsolete and wrong). Then the existing contract checks: referenced models registered in the live config, host liveness, derived-model presence. `-RoundTrip` additionally makes every referenced model answer a prompt AND runs a **capability probe** (coder → python function, reasoner → arithmetic w/ reasoning, general → Q&A; embed models → `/api/embeddings`) plus a **latency benchmark** against per-model ms budgets. `-Bench` implies `-RoundTrip` and turns over-budget into FAIL (instead of WARN) and prints a summary table. Applies intent + benchmarks per-profile, and gates the `localhost` server-baseURL WARN to `dev-workflow-server` only. Emits PASS/FAIL/WARN/SKIP; WARN = state to fix (e.g. blank `OLLAMA_SERVER_BASE_URL`, unprovisioned host, missing installs), FAIL = broken; exit 1 on any FAIL. A `-RoundTrip` model returning `EMPTY content` is the reasoning-model max_tokens trap — see Gotchas.
- **CI (`.github/workflows/checks.yml`, since 2026-10-13) runs on every pull request and push to `main`:** a Linux job parses every `.ps1` (the `ParseFile` wrapper above), runs `bash -n` on every `.sh`, the Python unit tests and a manifest parse; a Windows job (`windows-latest`, PowerShell 7, Node 24.18.0, opencode 1.18.34) runs every guard through **`.\tests\run-guards.ps1`**, which is the same run on the desktop in one command (`-Only`, `-Exclude`, `-TimeoutSec`, `-LogDir`; logs are a CI artifact). The guards are Windows-first (stand-in `opencode.cmd` shims, `%TEMP%`, `taskkill`), so a Linux session cannot run most of them: that job is where a script change is first exercised as the desktop runs it. Not in CI, because they need live hosts: `test-profiles.ps1` (and `-RoundTrip`/`-Reliability`), `test-tasks.ps1` runs and `test-toolcalls.ps1`. A PR lists those under Verification as run on the desktop, or as not run. A new guard needs no workflow edit (`run-guards.ps1` finds `tests/test-*.ps1`); a new live-host script that is named `test-*` goes on its `$Excluded` list with the reason.
- Bash syntax: `"C:\Program Files\Git\bin\bash.exe" -n <script>`; behavior: `bash -c 'source models/catalog.sh && catalog_list'`.
- PowerShell: `.\desktop\scripts\models.ps1 -List`.
- Server runtime checks: `./server/scripts/status.sh` (also runs `nvidia-smi`), `curl :11434/api/ps`.
- OpenCode: `opencode debug config` (does it load + resolve `{env:}`), `opencode debug providers` (provider status).
- `.\tests\test-revert-source.ps1` is the regression guard for the failsOnOld revert in `test-tasks.ps1` (`Save-SourceFiles`, `Restore-SourceFiles`, `Invoke-WithSourceReverted`, which replaced a `git stash push` / `pop` on 2026-10-03): the real functions against throwaway repos for one-file, two-file and bare-string `srcRevertFiles`, bytes that are not text restored byte for byte, a source path the base lacks, a model that committed, and two worktrees of one repo graded at the same time. Run it after touching how `test-tasks.ps1` reverts the source or builds native argument lists — a nested array passed to `Run-Native`'s `[string[]]` parameter becomes one space-joined argument (`a.ts b.ts`) and the harness silently stops being able to grade multi-file tasks, and `refs/stash` is shared by every worktree of a repo, so two tasks of one repo graded at once pushed and popped each other's stashes.
- `.\tests\test-cap-hit.ps1` is the regression guard for the writes gate's cap-hit classification (`Get-TranscriptEnding`, `Test-OutputCapHit` in `test-tasks.ps1`, plus `Format-ContextOverflowWarning`, which the real writes-gate block it runs ends on; `Get-ModelOutputLimit` in the OpenCode adapter, `tests/agents/opencode.ps1`): synthetic transcripts for each edge plus committed real ones the 2026-09-29 audit classified (cap before and after edits, a mid-run cap that recovered, real liar mode). Run it after touching how the harness reads a transcript's last step.
- `-Reliability` (on `test-profiles.ps1`) is the write-discipline canary: single-write prompt through `opencode run` on every tool-capable main seat, FAILs on >1 write call (the regression that once unseated `qwen3:14b`) or on zero (liar mode). Slow — runs a real task per seat.
- `.\tests\test-tasks.ps1` is the task-veracity benchmark: fixed prompts through the real `opencode run` tool loop in throwaway worktrees (`tests/.worktrees/`, git-ignored), graded mechanically on scope / suite / failsOnOld / typecheck. **Everything OpenCode-specific lives in one adapter, `tests/agents/opencode.ps1`** (`-Agent`, default `opencode`, on both scripts): starting and continuing a run, reading its transcript into neutral events, its version and config. The grading and every analysis of a run read only those events, so another agent is one sibling adapter file and a new era (owner, 2026-10-10: the daily client may move off OpenCode; `test-agent-adapter.ps1` below). A task's manifest `testEnv` (variable → value, `null` = unset) pins the environment the test command **and the model's own shell** run under, and the run JSON records it; `asohav-02`, `asohav-05`, `asohav-07` and `asohav-08` (`DATABASE_URL` unset) and `lfc-02` (`MANAPOOL_API_KEY` unset) carry one — without it a gate result depended on whatever the harness process held (`docs/implementation-tasks.md` → DP12 addendum). `failsOnOld` is the load-bearing gate — revert source, keep the model's test, suite must FAIL. **A run is graded only if `opencode run` exited 0.** opencode exits 0 even when the model answers in prose and writes nothing, so `writes = 0` on an exit-0 run is liar mode unless the last step ended on the output cap (finish reason `length` at `limit.output`, no text or tool call in that step) — the writes gate now tells the two apart and every run JSON records `outputCapHit` (both stay FAILs; rows before 2026-09-30 have no such field, so classify them from the transcript); **any non-zero exit is infrastructure** — unreachable provider, bad model id, crash — and yields a FAILed run, an `_INFRA_`/`_TIMEOUT_` transcript, and **no `tasks-summary.tsv` row**, because a run that never reached the model measured nothing. That distinction is not academic: it used to fall through to the writes gate, which is how six unreachable-endpoint transcripts ("Cannot connect to API", 307 bytes each) were recorded as a "6/6 liar mode" capability finding for node3 and then cited in a config change — see `docs/roadmap.md` → "Node3's `qwen3:8b` 'liar mode' was never liar mode" and `tests/results/README.md`. `typecheck` is `SKIP` for every task that defines no `typecheck` block (24 of 27 now; only `kane-01`, `lfc-01` and `lfc-03` define one) (it was `PASS`, claiming a clean compile for a `tsc` that never ran), so **any parser over that TSV must tolerate `SKIP`** (in `failsOnOld` too since 2026-10-03: it is `SKIP` when the suite is already red with the model's change, because a suite that fails either way measures nothing; 30 earlier rows read `suite: FAIL, failsOnOld: PASS` for the same reason, see `tests/results/README.md`), plus the `n/a`/`NOT_RUN` of the one hand-recorded row. See its header + `tests/tasks/`.
- `.\tests\run-tasks-batch.ps1` wraps it for day-to-day use: ensures every task's local `bench/*` branch exists (idempotent — see "Task-veracity benchmark: task set expansion" in `docs/roadmap.md` for the branch↔commit table), then interactively prompts for which task(s), which model(s), and how many repeats of each, and runs `test-tasks.ps1` once per (task, model, rep) — rep-outer within each model (every task's rep 1, then every task's rep 2, so a cell's replicates are a pass apart; `-BackToBack` keeps them adjacent), on **one opencode version**: it reads `opencode --version` at the start, checks it before every run and stops if it changes, and its preflight says whether autoupdate is pinned. `-SetupOnly` just creates missing bench branches and warns when a pinned base or acceptance commit is not on origin (asked of origin itself, from an empty repo), with the `git push` that fixes it; `-SkipSetup` skips straight to the prompts. **Both pickers are data-driven — adding a task or a model is never a script edit.** Tasks read from `tests/tasks/manifest.json`. **Every task is pinned:** it carries a full 40-hex `benchBaseCommit`, and `test-tasks.ps1` (`Resolve-TaskBase`) runs that exact commit — the `branch` is only a label, a local branch sitting elsewhere is a WARN, and a pin missing from the repo is an error. A task's base therefore cannot move under the corpus; to change one, add a NEW task id, because two bases under one id make the rows incomparable. All 27 pins are on GitHub (26 on `main`; `kane-01`'s `92a8ed0` is `review-gate/deck-validity` and PR #82's head); lfc-03's owner acceptance tests are pinned too (`acceptance.commit`, `3215aaf`, on GitHub as `bench/status-guard-throw` since 2026-09-30), and so are the 15 acceptance blocks added with the 18 tasks of 2026-10-03, whose oracle is the upstream fix commit's own test file (on `main`; `docs/roadmap.md` → "Task set expansion II") (`docs/roadmap.md` → "Correction (2026-09-30)"). Models read from `tests/run-tasks-models.tsv` (`tag engine hosts desc` since 2026-10-16: a row per tag and engine the toolcalls probe measured PASS on, with its eligible hosts; one tag on two engines is two rows) intersected against what each live host serves, asked through the engine adapters (`llamacpp-<host>` needs `LLAMACPP_<HOST>_BASE_URL`; a probe result is stale on host + engine + engine version, and both probe logs are read) — so a new tool-capable model is one TSV row, and a down host or an unpulled tag simply stops being offered. **Three modes (asked first, or `-Mode`):** `Tasks`, `Probe` (runs `test-toolcalls.ps1` on every host that answers, logs each result with host + Ollama version to `tests/results/toolcalls-summary.tsv`, and adds every current-version PASS to `run-tasks-models.tsv`), and `Both` (probe, then batch every available seat whose probe PASSes on its host's *current* Ollama version). Seats with a current-version FAIL, or that the live `opencode debug config` doesn't know, are dropped before they can burn a run as `_INFRA_`. `-OnlyMissing` skips task × model pairs that already have a graded row, and models with the fewest graded runs go first. Everything is also a parameter (`-Mode -Tasks -Models -Reps -OnlyMissing -Yes`). "One run of everything with no data yet" is `.\tests\run-tasks-batch.ps1 -SkipSetup -Mode Both -Models new -Tasks all -Reps 1 -OnlyMissing -Yes`. **Before the first run it checks every host it is about to drive with `/api/tags` and refuses to start against one that is not answering** — including `$env:OPENCODE_SMALL_MODEL`'s host, which matters because `dev-node3.sh` points that at the server that has not POSTed since 2026-09-16. Sequential by design — true concurrency (different task IDs only, never the same one twice) still means two separate terminals running `test-tasks.ps1` directly, per the worktree-keyed-by-task-id constraint. Tasks of one repo are safe together since 2026-10-03; before that the failsOnOld revert used the repository-global `git stash`, so two terminals grading tasks of one repo could pop each other's stash (the gate verdicts themselves were computed before the pop, but the acceptance run and the next worktree state were not safe).

Each rejection is recorded as `infrastructure` (no run JSON), `tampered`, `acceptance`, `suite` or `scope`; one row per task goes to `retry-summary.tsv` (attempts, accepted attempt, reasons, seconds, output tokens, run files), and the run ends with the design's falsifier (`Get-RetryFalsifier`: more than 1.5 attempts per task, or the cap reached on more than 15% of tasks). With the tasks' own hidden tests shown, the selector is an oracle; with a planner's tests (`-HarnessArgs @{ AcceptanceDir = "planner/{task}" }`, experiment 3) the dispatcher decides on the run JSON's `selector`, and the summary and the end of the run count the false positives and false negatives against the hidden tests. Guard: `.\tests\test-retry-loop.ps1` (23 checks: the verdict and falsifier functions on synthetic cases, then the real loop against a stand-in harness that scripts each attempt's outcome: accepted at once, after each kind of rejection, the cap, the arguments every attempt gets, the summary rows, the falsifier both ways). Controls: a loop that ignores tampering fails 2 checks, one that does not show the tests fails 1.
- `.\tests\test-engine-adapter.ps1` is the regression guard for the **engine** adapter boundary (Phase 2 of "Replacing Ollama", 2026-10-16). `tests/engines/ollama.ps1` (extracted from `test-tasks.ps1`, behaviour unchanged) and `tests/engines/llamacpp.ps1` define one interface: `Get-EngineBaseUrlVar`, `Get-EngineBaseUrl`, `Test-EngineAlive`, `Get-EngineVersion`, `Format-EngineVersion`, `Get-EngineServedModels`, `Get-EngineServedContext`, `Get-EnginePromptLossSetup`, `Get-EnginePromptLoss`, `Get-EnginePromptLossText` and `Get-EngineGpuPlacement`. `test-tasks.ps1` loads one by the provider prefix of `-Model` (`ollama-*` / `llamacpp-*`; any other provider records "not checked" as before).
  - **llama.cpp specifics:** the version is the router's `/props` `build_info`. The served context is the seat's `--ctx-size` in `GET /models`, else `/props?model=<seat>&autoload=false`, so a check never loads a seat. Prompt loss is "not applicable: refused explicitly". GPU placement goes over ssh: `nvidia-smi --query-compute-apps` plus `ps -eo pid,args`, matching the child whose args carry `--alias <name>`, where the name is the seat's tag, its router id or one of its aliases from `/models` (the router rewrites colon ids: tag `qwen3.6:35b-a3b-coding`, child `--alias qwen3.6:CODING`; `/models` unreachable falls back to the tag alone). The ssh host is `LLAMACPP_<HOST>_SSH`; unset gives `unchecked` with a note naming it.
  - **Every run JSON records `engine` (name, version, baseUrl)** from 2026-10-16. `ollamaVersion`, `servingEngine`, `numCtx`, `promptTruncation` and `gpuPlacement` keep their meaning for Ollama runs; for a llama.cpp run `ollamaVersion` is null.
  - Covered: interface and boundary (outside comments, `test-tasks.ps1` names no `/api/` endpoint, `server.log` or Ollama-only function); the real functions of both adapters against a stand-in `Invoke-RestMethod`; the ssh path with a stand-in `ssh` (GPU, CPU-only, a seat beside it, not loaded, ssh failing, variable unset); and the real harness end to end for an Ollama, a llama.cpp and a hosted provider. Controls: a missing function, a missing `$script:EngineName`, and a `/api/` call put back.

  - Run it after touching either adapter or an engine call in `test-tasks.ps1`.
- `.\tests\test-context-exceeded.ps1` is the regression guard for the **contextExceeded** outcome (2026-10-16). An agent exit of 1 whose only errors are context overflows and that did not recover (`Get-OverflowRecovery`) is exit **-6**, a `_CTXEXCEEDED_` transcript and no summary row, with a FAIL line that begins "Context exceeded". Before 2026-10-16 it was `_INFRA_` with the detail "overflow killed the run". A timeout that holds unrecovered overflows (the trial's `kane-08` loop) stays `_TIMEOUT_` and names them. Exit codes: -1 timeout, -2 job died, -3 truncated, -4 no session, -5 CPU-only, -6 context exceeded. Covered: the real `test-tasks.ps1` with a stand-in opencode for unrecovered, recovered, overflow plus another error (`_INFRA_`), a timeout with overflows, and a clean run; a control without the -6 branch fails. Run it after touching how a run's exit is classified.
- `.\tests\test-opencode-run.ps1` is the regression guard for `Invoke-AgentRun` in the OpenCode adapter (`tests/agents/opencode.ps1`; the real function, a stand-in `opencode` first on `PATH`): a normal run, a non-zero exit, a timeout, and the job's own PowerShell process dying mid-run.
