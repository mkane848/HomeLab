- **Files copied from Windows to the server lose the exec bit** — run `./make-executable.sh` after scp. (Syntax-check local .sh files from Windows first with Git bash.)
- **Tool-calling is decided by the chat template and weights, not by the model family, and a probe PASS is necessary but not sufficient.** Today's probe: `.\tests\test-toolcalls.ps1 -Engine llamacpp -EngineHost http://SERVER_IP:8090 -Model <tag>` (llama-server's `/v1/chat/completions`). A verdict is per engine and build, so the Ollama-era results that follow are history (Ollama removed 2026-11-21): re-probe before seating. Measured against `/api/chat` with a tool schema. On Ollama 0.34.0, re-measured on 0.34.1 (2026-09-19, every result reproduced, including each failure's mode — `tests/results/toolcalls-0.34.1.txt`), 5 of the 13 then-installed models passed: `qwen3:8b`, `qwen3:14b`, `qwen3.5:9b`, `qwen3-coder:30b-a3b` (the review-gate auditor seat) and `devstral:24b` (which partially offloads). That batch was mostly `qwen2.5-coder` and `deepseek-r1` models, which is why it read as "only qwen3". **Re-probed 2026-09-22/23 (desktop on 0.34.3, node3 on 0.34.2; `tests/results/toolcalls-summary.tsv`), 13 of 22 models pass:** those five plus `devstral-small-2:24b`, `laguna-xs-2.1`, `nemotron-3.5-lightning`, `north-mini-code-1.0` and `qwen3.6:35b-a3b-coding` on the desktop, and `lfm2.5:8b`, `ministral-3:8b` and `ornith:9b` on node3. Failing: the whole `qwen2.5-coder` family (`3b`/`7b`/`14b`/`-16k`) returns **empty** `tool_calls` and prints the call as chat text; the whole `deepseek-r1` family (`14b`/`-16k`/`-32k`/`-0528:8b`) ignores the tool and answers in prose. The Qwen2.5 template needs `<tool_call></tool_call>` tags the coder weights never emit; not caused by the `num_ctx` bake (a pristine re-pull behaves the same). `ollama show` listing a `tools` capability only means the *template* supports tools. **Any seat that must read/edit/run needs a probe PASS and task-loop evidence** (`tests/results/README.md`) — a non-tool-calling coder or reasoner is a chat box that will claim it edited files it never touched, and so can a probe-PASS seat (`lfm2.5:8b` made 0 writes on 8 of 8 tasks, `devstral:24b` on 4 of 4). `qwen3.6:35b-a3b-coding` is the default main seat (since 2026-10-03; on the server via `dev-workflow-server` since 2026-10-13). Its predecessor `qwen3:14b` was once unseated for issuing 6 write calls for a single request — if you see repeated `← Write` lines in a session, drop back to `qwen3:8b`. See `docs/troubleshooting.md` → "Agent 'says' it edited a file" and "Passing the probe is necessary, not sufficient — watch for repeated calls". **`glm4:9b` was never part of that 13-model batch and is a separate measured result:** probed for real on node3 (2026-09-20, `tests/test-toolcalls.ps1 -Model glm4:9b -OllamaHost http://NODE3_IP:11434`) — **FAIL**, ignored the tool entirely and answered in prose ("To write the text 'hello' to a file..."), same failure shape as the `qwen2.5-coder`/`deepseek-r1` families above. `opencode/global/opencode.jsonc`'s `ollama-node3` block previously declared `"tool_call": true` for it with no measurement behind that claim — corrected to `false` now that one exists. `qwen3:8b` was probed on the same node3 host in the same session and **passed** (62.3s, real `write_file` tool call), confirming the qwen3 family's tool-calling holds across the CUDA backend too, not just Vulkan/desktop.
- **OpenCode silently drops unknown model keys.** `context_window` and a bare `input` are not in the schema; they vanish without an error and the model resolves with **no limits**, so OpenCode never trims the prompt and reserves ~8192 for output. Result: a 46,505-token prompt at a 16k model, `truncating input prompt limit=8194 prompt=46505 keep=4`, system prompt destroyed, 5-minute 500. Correct keys (OpenCode 2.x, the template since 2026-11-27): `limit: { context, output }` and `capabilities: { tools, input, output }`; 1.x wrote `modalities` and `tool_call`. **Always confirm with `opencode --standalone debug config` that the entry's `info` still has `limit`** — the template proves nothing.
- **Preamble budget.** Every MCP server's tool schema and every installed skill's description ride in *every* request. That is why global config ships zero MCP servers and 2 skill sources (`$GLOBAL_SKILL_SOURCES` in `sync-skills.ps1`; was 5 servers + full skill set = 46.5k tokens, now ~11.4k). Projects opt in via their own `opencode.jsonc` — see `opencode/project-override/opencode.jsonc`. Measure with `opencode run ... "Reply with exactly: OK"` and read the request's prompt token count from llama-server's log (`docker logs llamacpp-server` on the server; before 2026-11-21, `task.n_tokens` in the Ollama log). **Beware the `~/.claude` rider:** OpenCode auto-loads every skill under `~/.claude/skills/<name>/SKILL.md` as a "Claude-compatible" skill and its description rides in every request — the Claude Code plugin's synced skills (`~/.claude/skills/synced/`, 10 files, 167 KB) added ~2.5k tokens of standing overhead unaccounted for by any `$GLOBAL_SKILL_SOURCES`. Measured 2026-09-20 on the desktop: OK probe 16,851 tokens (113 s prefill) with them, 14,364 tokens (84 s) with `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1`. That env var is set in every live profile and as a User-level default; keep it set — a bare `opencode` launch without it silently reloads the synced skills.
- **opencode upgrades itself unless told not to, and the benchmark's "same config" includes its version.** With `"autoupdate": true` opencode installs *patch* releases whenever a TUI starts (a minor or major release only notifies) — and never from `opencode run`, so the binary changes under a running batch when OpenCode is opened on the same machine ([`upgrade.ts`](https://github.com/sst/opencode/blob/2fa3363c924c5c3e367b84a87ae478296a0ed59b/packages/opencode/src/cli/upgrade.ts), read at that commit, 2026-09-29; the global config is the one it consults). The results corpus took three versions in ten days (1.18.31, .32, .33), so replicates straddled versions. The global template set `"autoupdate": "notify"` (it still said when an update existed), and the desktop still moved to 2.3.2 by itself on 2026-11-21. Since 2026-11-27 it sets 2.x's `"update": "disable"`; `OPENCODE_DISABLE_AUTOUPDATE=1` pins it too. Upgrade with `opencode upgrade` between batches and treat the new version as a new era: a same-config attempt shares prompt sha, `numCtx`, engine version (Ollama's until 2026-11-21, llama.cpp's build since) **and** opencode version (`docs/adversarial-review-2026-09-29.md` §7). Verify with `opencode --standalone debug config` (`update`) — the batch preflight also reports it.
- **OpenCode 2.x resolves `{env:...}` and config overlays in its shared background service, not in the shell that launched the client** (measured 2026-11-21, v2.3.2). 2.x starts one service per machine and every client attaches to it ([OpenCode 2.0](https://anoma.ly/notes/opencode-2-0/)). With `OPENCODE_MODEL` set in the shell, `opencode debug config` showed the User-level default (`ollama-desktop/qwen3:8b`) and `opencode --standalone debug config` showed the shell's value. `OPENCODE_CONFIG` and `OPENCODE_CONFIG_CONTENT` were likewise ignored without `--standalone`. So a profile launch, a harness run and a config-overlay experiment all need `--standalone` (a private server that inherits the caller's env), placed before the subcommand. `desktop/scripts/opencode.ps1` adds it on 2.x (`opencode-standalone.ps1`; guard `tests/test-opencode-profiles.ps1`). The harness adapter does not yet (`docs/opencode-2-migration.md`, step 3).
- **OpenCode 2.x refuses a config-defined provider without `npm`** (`provider.no-route: Unsupported package for <model>`; v2.3.2, 2026-11-21). 1.x gave it `@ai-sdk/openai-compatible` by itself, while 2.x normalizes the missing field to an empty `package`. Every local provider in `opencode/global/opencode.jsonc` states `"package": "aisdk:@ai-sdk/openai-compatible"` (since 2026-11-27; 2.x's own migration writes that for 1.x's `"npm": "@ai-sdk/openai-compatible"`), and a new provider must too. Check with `opencode --standalone debug config`: each provider's `package` should be `aisdk:@ai-sdk/openai-compatible`.
- **Context length** is set per model in the router preset: the explicit `c` in each section of `server/llamacpp/models.ini` (node3: `node3/llamacpp/models.ini`). It equals `num_ctx` in `models/server-seats.tsv` and `limit.context` in `opencode/global/opencode.jsonc` — three halves of one contract, checked by `tests/check_config_drift.py` and `server/scripts/llamacpp-check.sh`; changing one without the others brings back over-long requests. One slot per model (`parallel = 1`), because `c` is shared across slots. The main seat serves 65536, `qwen3:8b` 32768, the CPU 3b 16384. (Until 2026-11-21 the desktop's Ollama baked `num_ctx` per model through `startup.ps1`'s `$contextModels`; that script is gone.)
- **VRAM: use measured numbers, never file size.** A GGUF's size on disk omits KV cache and compute buffers (1–3 GB more). `qwen3.6` (21.7 GB file) is larger than the server's 16 GB card: the experts of the first `n-cpu-moe` layers stay in system RAM (20, with a 4,096 batch, since 2026-11-04: 14.7 GB of VRAM), and its companion `qwen2.5-coder-3b-cpu` runs on the CPU. Check on the running server with `nvidia-smi` and `./server/scripts/status.sh`.
- **The desktop runs no models** (since 2026-11-21: Ollama removed, and its GPU has unresolved crashes). It is the OpenCode client and the harness run host. The old desktop facts (RX 6800 XT on Vulkan, never ROCm; flash attention costing prefill on Vulkan; `OLLAMA_KEEP_ALIVE=4h`) are history in `docs/archive/troubleshooting-incidents.md` and `CHANGELOG.md`.
- **PowerShell ⇄ bash output mangling**: piping Git-bash stdout into PowerShell renders as UTF-16/ANSI garbage. Redirect bash output to a file and read the file.
- **Never pass `gh pr create/edit --body "..."` inline from PowerShell.** Backtick is PowerShell's escape character (`` `n `` → newline), so every code span is eaten and stray backslashes litter the rendered PR (this happened on PR #19/#20 and had to be fixed with `gh pr edit`). Write the body to a file and use `--body-file`, then confirm with `gh pr view <n> --json body --jq .body`.
- **`$ErrorActionPreference = "Stop"` + native stderr**: a native command's stderr becomes a terminating error under Stop. Scripts that probe fallible hosts (e.g. ssh) must temporarily drop to `Continue` around the probe (see `sync-opencode.ps1`).
- **Reasoning models + small `max_tokens`** return empty content (budget burned on the `reasoning` block, `finish_reason: "length"`). Keep `max_tokens` ≥256 for DeepSeek-R1/Qwen3; don't blame the profile. The same trap lives in the task loop as `limit.output`: a run whose last `step_finish` has `reason: "length"` at exactly the configured `limit.output`, with no text or tool event in that step, hit the cap. The harness used to record it as `writes = 0` and label it liar mode; it now reports a cap hit and sets `outputCapHit` in the run JSON (`tests/test-cap-hit.ps1` guards it). Rows before 2026-09-30 predate that, and 8 of the 31 exit-0 zero-write rows since 2026-09-22 are this shape (`nemotron-3.5-lightning` 4 of 6, `ornith:9b` 3 of 4, `qwen3:8b` 1 of 1). Only `qwen3:14b` and `qwen3.6` are at 8192; every other tool-capable seat is at 4096. Check the finish reason before calling a seat a liar.
- **A long session can lose its task silently.** opencode (1.18.34) compacts on the last step's token count, not counting the tool output that step just added. One large `read` (up to ~50 KB, ~15k tokens) can carry the next request past `num_ctx` with no compaction first. Ollama (0.34.3) then dropped messages from the front, task prompt first, and logged it only at debug level. (llama-server, the only engine since 2026-11-21, refuses such a request with HTTP 400 `exceed_context_size_error` instead, which opencode treats as a context overflow: [llamacpp-trial.md](../llamacpp-trial.md).) Most models carry on without the task; `qwen3.5:9b`'s template refuses and returns a 500, "No user query found in messages", which is the same overflow and not a template bug.
  - Setting `limit.input` plus `compaction.reserved` makes opencode compact earlier. A trial of that cost more passes than it saved, so it is not adopted.
  - If a session suddenly asks what you want, it lost the prompt: restate the task.
  - See `docs/roadmap.md` → "Context overflow".
- **Unsetting an env var in PowerShell needs `[NullString]::Value`.** `[Environment]::SetEnvironmentVariable($n, $null)` (or `""`) removed the variable on pwsh 7.4 (.NET 8) but leaves it set to `''` on pwsh 7.5+ (.NET 9; node3 and the CI runner run 7.6.6), because PowerShell binds `$null` to a .NET string as `""`. Use `[NullString]::Value`, or `Remove-Item Env:NAME`, and check absence with `Test-Path Env:NAME`, not `IsNullOrEmpty`. Found by CI's first Windows run (2026-10-13); `tests/test-task-env.ps1` guards the harness's use.
- **`{env:...}` has no fallbacks.** OpenCode's substitution does not support `:-default`; `"{env:VAR:-http://…}"` resolves to an empty string and providers fail with `"/chat/completions" cannot be parsed as a URL`. Values must come from the active profile (or User-level env defaults on the desktop so OpenCode works without sourcing).
- **Docker on the desktop** won't start its engine unless `C:\Users\<username>\.wslconfig` has `[wsl2] gpuSupport=false` (workaround for a WSL ConfigureGpu signature error). The desktop runs Docker Desktop only for the Docker MCP server; the server runs llama-server in Docker.
- GPU access for the server container relies on nvidia-container-toolkit; if the container can't see the GPU, re-run the toolkit setup in `docs/troubleshooting.md`.
- **The server's container can lose the GPU silently, and the API keeps answering from the CPU.** Docker there uses the systemd cgroup driver on cgroup v2, and a systemd reload (a package install, the daily apt/snap timers) drops the container's device access: `docker exec llamacpp-server nvidia-smi -L` says `Failed to initialize NVML: Unknown Error` while the host's `nvidia-smi` looks fine. Seen 2026-10-12 at 11:12Z: `qwen3.6` loaded at 38 GB, `100% CPU`, and the first launch of the nudged round crawled for 31 minutes before it was noticed (stopped; no rows; on the Ollama container then; the llama.cpp compose file carries the same device nodes and GPU-aware healthcheck). **Before trusting any number from a remote engine, check the container's health (`status.sh`) and the in-container `nvidia-smi -L`;** the harness checks it after each run since 2026-10-12 (`gpuPlacement` in the run JSON; a seat loaded with `size_vram` 0 is exit -5 with a `_CPUONLY_` transcript and no row, and the batch stops driving that host; `tests/test-gpu-placement.ps1`), so rows from before that date have no check behind them. Fix, cause and the prevention (explicit device nodes plus a GPU-aware healthcheck; it survived one `sudo systemctl daemon-reload` on 2026-10-12, so re-test after Docker, driver or toolkit upgrades): `docs/troubleshooting.md` → "Container lost the GPU".
